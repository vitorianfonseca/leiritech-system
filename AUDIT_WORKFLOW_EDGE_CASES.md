# Workflow Edge Case Audit

**Scope**: Backend-authoritative enforcement of WORKFLOW_SPEC.md §1 (state machines / invalid-transition tables) and §2 (business rules), focused on *implemented* features only. Cross-checked against `.forge-cache` and direct reads of `backend/app/services/*.py`, `backend/app/repositories/*.py`, `backend/app/core/permissions.py`, `backend/app/api/routes/*.py`.

Findings that are purely "feature X doesn't exist yet" (e.g. no task-archive endpoint, no opportunity-archive/reopen endpoint, no role-change endpoint) are **excluded** here — those belong to `AUDIT_WORKFLOW_COMPLETENESS.md` (workflow-completeness-auditor). This report only covers edge cases in code paths that ARE reachable today.

**Positive controls confirmed working** (checked so they aren't re-flagged elsewhere):
- BR-040 single-active-timer race: `time_service.start_timer` has both a pre-check AND a DB partial-unique-index backstop wrapped in `try/except IntegrityError` → clean 409 (`backend/app/services/time_service.py:81-132`).
- BR-002/H7 Membro horizontal-access boundary consistently returns 404 (not 403) across `project_service`, `task_service`, `opportunity_service`, `proposal_service`, `company_service`.
- BR-008 financial gate (`RequireFinance` dependency) consistently 403s a Gestor without `payments_grant` (`backend/app/api/dependencies/auth.py:127-135`).
- Pagination bounds (`page ge=1`, `page_size ge=1 le=100`) are uniformly enforced (422) across every list endpoint — no page=-1/page=999999/limit=0 issue found.
- BR-044 manual-entry 24h boundary is `>` (not `>=`), so exactly-24h is correctly **allowed** (`backend/app/schemas/time.py:19,39`).
- AUTO-04 proposal expiry boundary is `valid_until < today` (strictly before), so a proposal is valid through the end of its `valid_until` day (`backend/app/repositories/proposals.py:116-128`) — a defensible, consistent boundary choice.
- BR-045 dependency gating correctly treats an archived blocking task as resolved rather than a permanent lock (`backend/app/repositories/tasks.py:154-168`).
- BR-062/H6 company-archive blockers correctly include won-but-unconverted opportunities (`backend/app/repositories/crm.py:141-172`).

## Findings

| # | Severity | File | Line(s) | Description | Recommendation |
|---|----------|------|---------|--------------|----------------|
| 1 | CRITICAL | `backend/app/services/user_service.py` | 121-143 (guard at 128) | **BR-005 last-Admin race**: `deactivate_user` does `SELECT count(active admins)` then `UPDATE status` with no row lock (`SELECT ... FOR UPDATE`), no version column, and no unique/check constraint backstop. If exactly 2 Admins exist and each concurrently deactivates the other (or is deactivated by a third actor in two near-simultaneous requests), both transactions read `count=2` (passes the `<=1` guard), both commit, and the system ends up with **zero active Administradores** — an unrecoverable state without direct DB access. This is the exact scenario the task named ("last Admin's account edited/demoted concurrently") and it is not race-safe. | Wrap the count-check + update in a single `SELECT ... FOR UPDATE` over the admin rows (or add a Postgres check constraint / trigger enforcing `count(active admins) >= 1`) so the second concurrent transaction fails with 409 instead of silently succeeding. |
| 2 | CRITICAL | `backend/app/services/opportunity_service.py` | `_assert_open` 185-191, `win_opportunity` 312-334, `lose_opportunity` 337-360 | **BR-013 won→lost race bypasses the invalid-transition table**: both `win_opportunity` and `lose_opportunity` read `opp.outcome`, check it's not already terminal, then write. Under READ COMMITTED with no row lock/version check, two concurrent requests (one "Marcar como ganha", one "Marcar como perdida") on the same open opportunity can both pass `_assert_open` before either commits. The result is an opportunity that ends up `lost` having genuinely passed through `won` — precisely the transition the spec's invalid-transition table says "MUST be blocked" ("`won` → `lost` — Cannot lose an already-won deal"). Unlike the timer (finding above the table), there is no DB constraint backstop here at all. | Use `SELECT ... FOR UPDATE` on the opportunity row (or an optimistic `WHERE outcome = :expected` on the UPDATE, checking `rowcount`) before applying `won`/`lost`, converting the loser to a 409 `OPPORTUNITY_ALREADY_CLOSED`. |
| 3 | CRITICAL | `backend/app/services/project_service.py` (745-815) + `backend/app/services/opportunity_service.py::convert_opportunity` (363-410) + `backend/app/models/project.py` (`opportunity_id` column, ~L45) | — | **Double-submit on won→project conversion creates duplicate projects**: `POST /projects/from-opportunity` calls `convert_opportunity` (read-only prefill) then unconditionally creates a new `Project`. Nothing checks whether a project already references this `opportunity_id` (no service-level check, and `projects.opportunity_id` has **no unique constraint** — confirmed by grep of the model and the initial-schema migration). A double-click, a retried network request, or two Gestores racing on the same "Converter em projeto" button all produce two independent projects both linked to the same opportunity/accepted proposal, both with their own phases/tasks/payment milestones. This also violates BR-013's stated intent ("single linked project unless **admin** explicitly adds another") since there is no admin-only gate on a second conversion either. | Add a partial unique index on `projects.opportunity_id WHERE opportunity_id IS NOT NULL`, and/or have `create_from_opportunity` check `project_repo` for an existing non-archived project on that opportunity and reject (409) unless the caller is Admin. |
| 4 | CRITICAL | `backend/app/services/project_service.py::change_state` (326-370) + `backend/app/core/permissions.py::can_manage_project` (104-110) | — | **Cancel-project permission-matrix violation**: §3 of the spec states "Cancel project: Administrador ✅ · Gestor 🔒/owner-with-grant" (i.e. requires an explicit grant, same class as the financial grant — design decision #9 explicitly ties this to "financial/margin consequences"). The implementation routes every lifecycle target — including `"cancelled"` — through the same `_require_manage`/`can_manage_project` check used for ordinary owner actions (start/pause/resume/complete). There is no grant flag consulted anywhere for cancellation (confirmed by grep — only `payments_grant`/`invites_grant` exist, no cancel-specific grant is checked in `project_service.py`). Any Gestor who owns a project can cancel it — a financially consequential, cascade-triggering action — without holding any special grant. | Add an explicit grant check (e.g. reuse `payments_grant` or a new `project_cancel_grant`) gating the `target == "cancelled"` branch of `change_state`, matching the matrix. |
| 5 | HIGH | `backend/app/services/invitation_service.py::accept_invitation` (128-185) and `::create_admin` in `user_service.py` (155-177) | — | **Race on invite acceptance / admin bootstrap surfaces as an unhandled 500, not a graceful 409**: both functions do "SELECT user by email → if none, INSERT" with no lock. `users.email` is unique at the DB level, so a genuine double-submit (double-click "Criar conta" on the accept-invite screen, or a network retry) can pass the pre-check twice, then hit an `IntegrityError` on `db.add(user)`/flush. Unlike `time_service.start_timer` (which explicitly catches this exact class of race and converts it to a clean 409), neither of these paths catches `IntegrityError`; it falls through to `app/main.py`'s catch-all `unhandled_exception_handler`, returning `{"code":"INTERNAL_ERROR"}` with HTTP 500 — a broken-looking failure for what is really just a benign double-submit, and worse, the first (successful) request's outcome is invisible to the user who saw the 500. | Wrap the insert in `try/except IntegrityError` in both functions and translate to `errors.conflict("Já existe um utilizador com este email.", code="EMAIL_TAKEN")`, mirroring the timer pattern. |
| 6 | HIGH | `backend/app/services/phase_service.py::_assert_phase_completable` (204-211) + `backend/app/repositories/phases.py::phase_task_counts` (32-40) | — | **Phase can be "completed" with zero tracked tasks (vacuous BR-051 guard)**: the guard is `if total > done: raise`. When a phase has **zero** non-archived tasks — e.g. a phase moved straight to `in_progress` before any task was ever added to it, or one whose only tasks were later re-parented to a different phase via `TaskUpdate.phase_id` — `total == done == 0`, so `0 > 0` is `False` and "Concluir fase" (`POST /phases/{id}/complete`) succeeds instantly with no work ever recorded. This is exactly the zero-data boundary the audit brief calls out, and it undermines the r2 "no waiver" resolution (C2): a phase can be closed out without a single task ever reaching `concluída`. | Require `total > 0` in addition to `total == done` before allowing the `completed` transition (a phase with no tasks should not be completable, or should require an explicit override reason). |
| 7 | MEDIUM | `backend/app/services/project_service.py::_assert_can_start` (373-392) + `backend/app/repositories/projects.py::unconfirmed_payment_milestone_count` (164-179) | — | **`planning`→`active` payment-milestone guard (BR-037/H5) is vacuously satisfied when zero milestones exist**: the guard only blocks when `unconfirmed_payment_milestone_count(...) > 0`. A project with **no payment milestones at all** (none created during/after conversion) has an unconfirmed count of 0, so the guard passes silently — the project goes live having never had its financial tracking reviewed at all, which is a stronger bypass of BR-037's intent than merely skipping confirmation of an existing milestone. | If the project has a non-null `contracted_value` (i.e. it's a commercial engagement), require at least one payment milestone to exist (and be confirmed) before allowing `active`; otherwise document the zero-milestone case as an intentional non-billable-project exemption. |
| 8 | MEDIUM | `backend/app/services/finance_service.py::update_milestone` (182-213) vs `_apply_partially_paid` (320-341) | — | **Editing `amount` after a partial payment is not re-validated against `received_amount`**: `update_milestone` only blocks edits when `status in ("paid","cancelled")`. A milestone in `invoiced`/`partially_paid`/`overdue` can have its `amount` field lowered (e.g. via `PATCH`) below the already-recorded `received_amount` — a value that was itself validated at `0 < received_amount < amount` at the time it was set (line 332) — leaving the milestone in an inconsistent state (`received_amount > amount`) with no re-check anywhere, and no repair path other than a further manual edit. | In `update_milestone`, when `amount` changes and `milestone.received_amount` is set, re-validate `received_amount < new_amount` (or `<=` for the paid case) and reject with 409 otherwise. |
| 9 | MEDIUM | `backend/app/services/company_service.py::_assert_can_manage` (168-177) + `create_company` (112-138) | — | **A company created with no `owner_id` can never be archived by any Gestor**: `_assert_can_manage` requires `company.owner_id == user.id` for a Gestor; `owner_id` is nullable and `create_company` does not default it to the creator. A Gestor-created company left without an explicit owner becomes permanently un-archivable by any Gestor (only an Admin can act on it), with no error message steering the user to "assign an owner first" — the 403 message ("Só pode arquivar empresas de que é responsável.") is misleading when the real issue is a missing owner, not the wrong owner. | Default `owner_id` to the creating user in `create_company` when not supplied, or have `_assert_can_manage` explicitly special-case `owner_id is None` with a clearer message directing the Gestor to claim ownership first. |
| 10 | LOW | `backend/app/services/time_service.py::update_entry` (205-244) | 214-223 | **BR-044 validation is skipped when only `started_at` is edited on a still-running timer**: `_assert_interval` is only called `if new_ended is not None` (line 222). If the caller PATCHes a currently-running entry's `started_at` (e.g. pushing it into the future) without touching `ended_at`, no future-date/interval check runs at all — the running timer's start can be set arbitrarily. Blast radius is limited (a later `stop_timer` clamps `ended_at = max(now, started_at)`, so a future `started_at` just yields a zero-duration entry rather than corrupt data), but the missing validation is still a real gap for the open-interval case. | Also validate `started_at` (not-in-the-future) when `ended_at` is null after the patch, not only when the interval is fully closed. |
| 11 | MEDIUM | `backend/app/services/project_service.py::_assert_can_archive` (406-413) | — | **Archiving a project silently force-stops another user's running timer with no notification**: unlike deactivation (BR-006, which is a direct action *on* the affected user), `_assert_can_archive` defensively calls `stop_running_timers` for *any* task in the project when an Admin/Gestor archives it, with no notification to the timer's owner. That user's "O meu trabalho" / timer widget will show a stale "running" state until they happen to refresh, and their logged duration is silently truncated by someone else's unrelated action. | Fire a notification (or at minimum log a distinguishable event) to the timer's owner when their running timer is stopped as a side effect of someone else archiving the project, mirroring the AUTO-12 "forgotten timer" pattern. |

## Coverage Summary

- **Workflows analyzed**: Opportunity/pipeline (§1.1), Proposal (§1.2), Project lifecycle + health (§1.3/1.4), Phase (§1.5), Task (§1.6), Payment milestone (§1.7), Milestone (§1.8), Invitation (§1.10), User (§1.11), Company archive (BR-062), Won→project conversion (BR-035..038).
- **Double-submit / race protection**: solid for BR-040 (timer) only; **missing or incomplete** for opportunity win/lose, last-Admin deactivation, won→project conversion, and invite/admin-bootstrap email uniqueness (findings #1, #2, #3, #5).
- **Null/empty-data paths**: mostly handled (empty contacts on conversion, zero-member visibility checks); one real vacuous-guard bug found (phase completion with 0 tasks, #6) and one vacuous-guard risk (payment-milestone confirmation with 0 milestones, #7).
- **Permission boundaries**: 404-vs-403 discipline for Membro is consistently correct everywhere checked; one real matrix violation found (Gestor cancelling a project without a grant, #4).
- **Referential integrity on delete/archive**: company archive blockers (BR-062/H6) correctly implemented; project cascade freeze/timer-stop (BR-053) correctly implemented but with a UX/notification gap (#11).
