# UX Interaction Audit

Scope: frontend/src/ (Next.js App Router, shadcn/ui). Findings gathered from
`.forge-cache/` (buttons.txt, forms.txt, dialogs.txt, empty-handlers.txt,
api-calls.txt, todos.txt) plus targeted reads of the pipeline Kanban, task
board (dnd-kit), timer system (BR-040), settings, proposals, and reports
surfaces. Automated empty-handler detection found 0 no-op `onClick`s; manual
review found no naive `onClick={() => {}}` patterns either — the codebase is
generally well-wired. The findings below are the real gaps: places where an
element *looks* fully functional but silently produces wrong/lost data, or is
inconsistent with an equivalent control elsewhere in the app.

## Interactive Elements Scanned
- Buttons found (cache): 369
- Forms found (cache): 134
- Dialogs/Modals found (cache): 37 (+ a few not indexed by the cache's regex, e.g. `won-dialog.tsx`, verified manually)
- Empty/no-op handlers (cache + manual re-check): 0
- Drag-and-drop surfaces reviewed: Pipeline Kanban (`pipeline-board.tsx`), Task Kanban (`task-board.tsx`) — both dnd-kit, both persist via API on drop
- Timer entry points reviewed (BR-040 single-active-timer): `task-side-panel.tsx`, `my-work-view.tsx`, `active-timer-card.tsx`, `timer-bar.tsx`

## Findings

| # | Severity | File | Line(s) | Description | Recommendation |
|---|----------|------|---------|-------------|----------------|
| 1 | CRITICAL | frontend/src/lib/api/proposals.ts | 472-490 (see also 331, 495) | "Upload"/"Replace" on a proposal PDF (`PdfUpload` in `frontend/src/components/proposals/pdf-upload.tsx:101-127`) looks fully successful — it shows the file card with a working-looking "Download" button — but the code is explicitly commented `LEFT-ON-STUB: no storage backend (#46)`. No file is actually persisted: the returned `file` object is synthesized client-side only, a subsequent read of the same proposal returns `file: null`, and the "Download" link points to `mockSignedUrl()` → `https://mock.r2.leiritech.pt/...`, a domain that does not exist and will fail to resolve if clicked. A user who uploads a proposal PDF, sends the proposal, then reloads the page will find the attachment silently gone, and anyone who clicks Download before that gets a dead link. | Either hide/disable the PDF upload control until R2 storage (issue #46) is wired, or show a persistent "not yet saved" indicator instead of presenting a normal file card + working-looking Download button. |
| 2 | HIGH | frontend/src/components/tasks/task-side-panel.tsx | 160-190, 327-337 | The task detail panel's timer Start/Stop button calls `timer.start()` directly with no confirmation, silently auto-stopping and finalizing whatever timer is currently running elsewhere (only a toast appears *after* the fact: "timer.switched"). This is inconsistent with the two other timer entry points — `my-work-view.tsx:213-222` (`handleStartTimer` opens a confirm dialog via `pendingTimer`/`setPendingTimer` before displacing a running timer) and `active-timer-card.tsx:100-108` (`handleStart` opens `setSwitchOpen(true)` before switching) — both of which explicitly implement the BR-040 "confirm before displacing" UX. A user working from a task's side panel can unknowingly cut off time being tracked against a different task, with no chance to cancel. | Add the same pre-start confirmation (check `timer.active` before calling `timer.start`) in `task-side-panel.tsx` that `my-work-view.tsx` and `active-timer-card.tsx` already use, for consistency and to prevent accidental mis-attributed time. |
| 3 | HIGH | frontend/src/components/settings/export-settings-view.tsx | 24-47 | Every "Export" button under Settings → Export downloads a CSV containing only the column headers and a single row of placeholder `—` values (comment: "Mock export: real backend streams the dataset; here we emit a valid CSV with the column headers + a sample row"), yet shows a success toast ("Exported") identical to a real export. A user has no way to tell this from a real data export — they will believe they exported their real dataset when the file contains no actual data. | Either wire the real export endpoint (`settingsApi` /export) before shipping, or clearly label the action as a preview/sample export until the backend is connected. |
| 4 | MEDIUM | frontend/src/components/catalog/catalog-detail-view.tsx | 69-77 vs 78-90 | The "Restore" action (`onClick={() => catalogApi.restore(item.id).then(refresh)}`) has no success toast and no `.catch` error handling, unlike the adjacent "Archive" action three lines below which does both (`await catalogApi.archive(...)`, success toast, implicit try via async function). If `restore()` rejects, the failure is silently swallowed — the button appears to do nothing and the item stays archived with no feedback to the user. | Make `restore` consistent with `archive`: await it, show a success toast, and catch/report errors. |
| 5 | MEDIUM | frontend/src/components/shell/quick-create.tsx | 27-33 | The global "Quick Create" menu implies each item creates something immediately, but only "Company" (`/crm/companies/new`) actually opens a create form. "Opportunity" → `/crm/pipeline`, "Contact" → `/crm/contacts`, "Task" → `/tasks`, and "Time Entry" → `/my-work` all just navigate to a list/board page, requiring the user to find and click a further "New …" button/dialog trigger once there. This under-delivers on the "quick" promise and is inconsistent within the same menu. | Either deep-link/auto-open the create dialog on arrival (e.g. `?create=1` query param consumed by the destination view) or rename these items to reflect that they navigate rather than create. |
| 6 | LOW | frontend/src/components/reports/report-section.tsx | 71-80 | The per-report CSV "Export" button is `disabled={!canExport}` (true whenever the report has zero rows) but has no `title`/tooltip explaining why it's disabled, unlike comparable disabled buttons elsewhere in the app (e.g. `lifecycle-actions.tsx` uses `title={...BlockedHint}`). A user seeing a populated report card but a permanently greyed-out export button (edge case: rows present in the UI table but the `csv.rows` payload happens to be empty) gets no explanation. | Add a `title`/tooltip such as "No data to export" when `canExport` is false. |
| 7 | LOW | frontend/src/components/projects/simple-tabs.tsx | 176-229 | The project "Ficheiros" (Files) tab renders a hardcoded `MOCK_FILES` array (`Briefing_inicial.pdf`, `Guia_de_estilo_v2.pdf`) for every project whose state isn't "planning", regardless of what files (if any) actually belong to that project. It is self-disclosed via a "coming soon" caption, and the file rows are not clickable (no download affordance), so this is a transparency/data-integrity nit rather than a broken interaction — flagging for awareness since it could confuse a user into thinking these are their project's real files. | Replace with a genuine empty state until file storage (F17) is wired, or clearly badge the section as a preview/placeholder. |

## Areas checked and confirmed WORKING (no issue)
- Pipeline Kanban drag-and-drop (`pipeline-board.tsx` `handleDragEnd` → opens `MoveOpportunityDialog` → `opportunitiesApi.moveOpportunity` on confirm, with undo toast).
- Task Kanban drag-and-drop (`task-board.tsx` `handleDragEnd` → `onRequestMove` → `tasks-view.tsx` `requestTransition`/`applyTransition` → `tasksApi.transition`, guarded by `checkTaskTransition`, with undo toast).
- BR-040 single-active-timer core guarantee: `timer-context.tsx` `startTimer()` always auto-finishes any other running timer before starting a new one — it is impossible to have two timers running client-side, even from the surface (task-side-panel) that skips the confirmation UX (finding #2 is about missing confirmation, not about the guarantee failing).
- `smart-table.tsx` search/filter genuinely filters the client-side dataset (not cosmetic).
- `reports/report-section.tsx` CSV export builds a real CSV from the same rows rendered in the table (unlike the Settings export, finding #3, which is synthetic).
- Dialog confirm actions checked: `WonDialog`, `LostDialog`, `ReopenDialog`, `MoveOpportunityDialog`, `BlockReasonDialog`, `ArchiveCompanyDialog`, `HealthDialog`, all form dialogs (Catalog/Company/Milestone/Cost/Payment/Phase/Task/Template/Proposal reject/resend) — all wire their confirm button to a real API call via `onSubmit`/`onConfirm` props traced back to `*Api.*` methods.
- Profile/Settings avatar & organization logo upload — uses `FileReader` → data URL persisted as part of the normal profile/settings save mutation (not a stub); works end-to-end.
- Quick actions (email/phone/website) on CRM cards render real `mailto:`/`tel:`/external anchors, never dead links.

## Architectural note (context, not a discrete finding)
Several domains still read/write through explicitly-labeled in-memory "MOCK implementation" API modules pending backend integration (e.g., earlier iterations of `lib/api/proposals.ts` seed data), while most create/read/update calls have since been "WIRED" to the real FastAPI backend via `lib/api/http.ts`. The one remaining functionally-broken gap from this transition is the proposals PDF file storage (finding #1) and the Settings CSV export (finding #3) — both explicitly called out above rather than treated as a blanket "everything is mocked" finding, since most CRUD flows are demonstrably wired to real endpoints.
