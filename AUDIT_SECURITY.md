## Positive findings (verified correct, not vulnerabilities)

- **BR-001 (server-side authorization)**: Every route module spot-checked (`projects.py`, `finance.py`, `reports.py`, `users.py`, `attachments.py`, `dashboard.py`, `auth.py`, `invitations.py`) uses FastAPI's `Depends`-based `CurrentUser` / `RequireGestor` / `RequireAdmin` / `RequireFinance` / `RequireInviteCapability` guards from `app/api/dependencies/auth.py`, and these are actually applied as parameter type annotations on the handlers (not just imported) — confirmed by reading the handler signatures directly, not just grepping imports.
- **BR-002 (404-not-403 enumeration guard)**: `project_service.get_project_or_404` correctly returns a generic 404 (`PROJECT_NOT_FOUND`) for a Membro who is neither the project's manager nor a member, rather than a 403, preventing existence-enumeration. `users.py`'s `_to_directory_entry` correctly redacts management-only fields for a Membro rather than blocking the whole endpoint. `attachments.py` calls `attachment_service.authorize_entity_access` as an explicit IDOR guard on every mutating and read operation.
- **BR-008 (financial gate) — correctly enforced elsewhere**: `finance.py` (all payment-milestone/project-cost/summary endpoints), `reports.py` `/financial` + `/financial/export`, and `dashboard_service.get_dashboard` (via `can_manage_financials`/`can_finance`) all correctly gate financial data server-side. This makes finding #1 (projects.py) look like an isolated oversight rather than a systemic gap — the team clearly knows and applies this pattern elsewhere, just missed it on the project detail/list endpoints.
- **JWT handling**: `JWT_SECRET` has a documented insecure-placeholder set and a `model_validator` that hard-fails app startup in production/staging if the secret is empty/placeholder/too short, if `DEBUG` is true, or if `DATABASE_URL` still matches the literal dev default. Token type (`access`/`refresh`/`reset`) is checked on every decode so a refresh token can never be used where an access token is expected. Password-reset tokens are stateless but bound to a fingerprint of the current password hash, making them single-use without needing a server-side revocation store.
- **SQL injection**: No raw string-interpolated SQL was found in application code paths reachable by user input. All free-text search (`companies`, `contacts`, `projects`, `tasks`, `proposals`, `opportunities`, `catalog`) uses SQLAlchemy ORM `.ilike()` with bound parameters (values passed as Python f-strings become bound parameters via the ORM, not raw SQL text), and `app/repositories/search.py` additionally has an explicit `escape_like()` helper for LIKE-wildcard escaping. The one `text(f"DELETE FROM {table}")` usage (`backend/app/database/seed_rich.py:274`) interpolates only from a fixed, hardcoded table-name list — not reachable from any user input — and is a dev/seed-only script.
- **XSS**: No `dangerouslySetInnerHTML` or raw `.innerHTML =` usage found anywhere in `frontend/src`.
- **Cookies**: Refresh token cookie is `httpOnly: true`, `secure` (prod), `sameSite: "lax"`, path-scoped. `sameSite: "lax"` on the refresh cookie also meaningfully reduces classic CSRF risk against `/api/auth/refresh` since it won't be attached to cross-site non-navigation requests.
- **Password policy**: A single `Password` field type (`min_length=PASSWORD_MIN_LEN, max_length=128`) is reused consistently across reset, change-password, and invitation-accept flows.
- **CSV export hardening**: Formula-injection hardening (`core.csv_export`, issue #59) is applied consistently across the report CSV export endpoints.
- **Secrets scan**: The only matches in `.forge-cache/secrets-scan.txt` are the shared test password (finding #5) — no hardcoded API keys, tokens, or production credentials were found in source, `.env.example`, or `docker-compose.yml`.
