# Workflow Logic Audit — LeiriTech

**Auditor**: Workflow Logic Auditor
**Scope**: Backend service-layer / API-layer enforcement of business rules (BR-001..084) per WORKFLOW_SPEC.md and forge-prd.md. Overlaps with DB-schema-level verification (BR-040 unique index, BR-047 cycle detection at schema level) are deferred to AUDIT_DATA_INTEGRITY.md; this report focuses on service/route enforcement.

---

## Summary

- **Rules examined**: 42 (the full BR-00x list given in scope)
- **Enforced**: 40
- **Partially enforced**: 0
- **NOT enforced**: 2 (both part of BR-035)

This codebase is unusually disciplined: nearly every service module has a docstring explicitly naming the BR it enforces, a single-seam design (e.g. `project_service.assert_child_forward_allowed`, `permissions.py` as the sole authorization predicate module), and defensive re-validation even where the schema already guards a rule. The one confirmed gap is a real, concrete cross-field validation the spec calls out explicitly (BR-035's 422-on-empty-contracted-value clause).

## Findings

| # | Severity | File | Line(s) | Description | Recommendation |
|---|----------|------|---------|-------------|----------------|
| 1 | **HIGH** | `backend/app/services/project_service.py` (`create_from_opportunity`, lines 745–815); `backend/app/services/opportunity_service.py` (`convert_opportunity`, lines 363–410); `backend/app/schemas/projects.py` (`ProjectFromOpportunity`, lines 150–162) | see above | BR-035 explicitly requires: *"Conversion form requires contracted value when proposal absent (422 if empty)"*. In practice: `convert_opportunity` prefills `contracted_value = proposal.value if has_proposal else opp.estimated_value` — i.e. when there is no accepted proposal it silently falls back to `opportunity.estimated_value` (itself an optional field with no required-ness at opportunity creation) instead of demanding a manual entry. `create_from_opportunity` then does `contracted_value = payload.contracted_value if payload.contracted_value is not None else prefill.contracted_value` and passes the result straight into `Project(...)` with **no check anywhere** that the final value is non-`None` before creating the project. If an opportunity is won with no accepted proposal AND no `estimated_value` set, `POST /projects/from-opportunity` succeeds and silently creates a project with `contracted_value = None` — the spec-mandated 422 never fires. This is not a frontend-only gap (there is no server-side check to bypass) — the guard is simply absent everywhere in the stack. | Add an explicit check in `project_service.create_from_opportunity` (or as a natural place, right after computing `contracted_value`): `if contracted_value is None and not prefill.has_accepted_proposal: raise errors.ApiError(422, code="CONTRACTED_VALUE_REQUIRED", ...)`. Do this at the service layer (not the Pydantic schema) since the requirement is conditional on `prefill.has_accepted_proposal`, which is only known after loading the opportunity/proposal. |
| 2 | **LOW** | `backend/app/services/opportunity_service.py:389-392` (`convert_opportunity`) | 389-392 | Related to Finding #1: falling back silently to `opp.estimated_value` when no accepted proposal exists partially defeats the *intent* of BR-035/C1 ("user MUST manually enter the contracted value") even in cases where a 422 might not technically fire (e.g. `estimated_value` happens to be set from the pipeline stage). The spec frames the manual-entry requirement as user-initiated data entry, not an auto-carried-over estimate; using `estimated_value` as an implicit default may under-count or over-count actual contract value without the human review the spec wants at this specific "core differentiator" handoff. | Consider making `contracted_value` `None` in the `ConversionPrefill` whenever `has_accepted_proposal` is `False` (rather than falling back to `estimated_value`), and let the frontend clearly show "no proposal — please enter contracted value" per BR-035/C1's stated UX, then enforce the 422 from Finding #1 to make the fallback impossible either way. |

No other gaps found among the 42 rules examined — every other rule in the assigned scope has a concrete, backend-authoritative enforcement point matching its spec text (correct status code family: 409 for illegal state transitions, 422 for missing-precondition validation, 403/404 for permission/scope boundaries).

- No frontend-only enforcement (button-hidden-but-API-open) pattern was found for any of the 42 rules audited — every rule that has a UI affordance (e.g. archive buttons, approve buttons, send-proposal buttons) has a matching backend guard that independently rejects the disallowed request. This is a notably strong result: the codebase's own documentation claim ("Enforcement is ALWAYS backend-side; the frontend role is never trusted (BR-001)") holds up under inspection.
